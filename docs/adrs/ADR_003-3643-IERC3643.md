## Context

The ERC-3643 standard defines a set of interfaces to support regulatory-compliant token operations. These interfaces are published under the ERC-3643 GitHub repository [https://github.com/ERC-3643/ERCs/blob/master/assets/erc-3643/interfaces] and include components for identity, compliance, recovery, freezing, and more.

Among them, IERC3643 is the main interface that directly extends IERC20, and serves as the entry point for most of the standard’s regulatory and operational features.

However, IERC3643 is defined as a monolithic interface, which is incompatible with our modular design principles based on the Diamond pattern (EIP-2535).

## Decision

### 1. Segregation of IERC3643 into functional modules

To align with our Diamond architecture, the monolithic IERC3643 interface will be split into independent functional modules, each implemented through:

- A dedicated interface (e.g., IERC20Freeze, IERC20Recovery, etc.)
- An internal contract that encapsulates the business logic and manages storage
- An external contract that exposes public methods and delegates to the internal logic
- A facet that connects the external contract to the Diamond via delegatecall

When functionality is shared across multiple modules—such as token metadata, pause state, or access control—logic is centralized in abstract internal contracts (e.g., ERC20InternalCommon, PauseInternalCommon)

### 2. Reuse of existing modules

To ensure compliance with ERC-3643 while maximizing modularity and reuse, the following strategy has been adopted:

- Reuse existing modules when method signatures and event definitions, are aligned with ERC-3643.
- Extend or redefine modules otherwise.

### 3. Conditional internal behavior

The internal logic of the modules dynamically adapts based on whether the environment has been initialized as ERC-3643 compatible. This configuration affects both access control and operation execution, enabling additional validations and specific restrictions to be applied only when the context requires it.

#### ERC3643 Metadata

**Option 1**

| Method                  | Module           | Interface        | Internal                | External        | Facet                | Comment                                          |
| ----------------------- | ---------------- | ---------------- | ----------------------- | --------------- | -------------------- | ------------------------------------------------ |
| `setName(string)`       | ERC3643 Metadata | IERC3643Metadata | ERC20Internal           | ERC20           | ERC20Facet           | Emits `UpdatedTokenInformation`. Only tokenOwner |
| `setSymbol(string)`     | ERC3643 Metadata | IERC3643Metadata | ERC20Internal           | ERC20           | ERC20Facet           | Emits `UpdatedTokenInformation`. Only tokenOwner |
| `setOnchainID(address)` | ERC3643 Metadata | IERC3643Metadata | ERC3643MetadataInternal | ERC3643Metadata | ERC3643MetadataFacet | Emits `UpdatedTokenInformation`. Only tokenOwner |
| `version()`             | ERC3643 Metadata | IERC3643Metadata | ERC3643MetadataInternal | ERC3643Metadata | ERC3643MetadataFacet | Returns current version string                   |
| `onchainID()`           | ERC3643 Metadata | IERC3643Metadata | ERC3643MetadataInternal | ERC3643Metadata | ERC3643MetadataFacet | Returns current onchainID address                |

- The IERC3643 interface methods related to **metadata** are partially implemented in `ERC20` and partially in `ERC3643Metadata`.
- The events and role modifiers affecting `setName` and `setSymbol` are applied in `ERC3643MetadataInternal` only if the 3643 extension has been initialized, while the actual storage update logic resides in `ERC20Internal`. Conflicts are handled in `ERC20InternalCommon`.
- The events, role modifiers, and storage update logic affecting `setOnchainID` are applied in `ERC3643MetadataInternal`.

**Option 2**

| Method                  | Module           | Interface        | Internal                | External        | Facet                | Comment                                          |
| ----------------------- | ---------------- | ---------------- | ----------------------- | --------------- | -------------------- | ------------------------------------------------ |
| `setName(string)`       | ERC3643 Metadata | IERC3643Metadata | ERC20Internal           | ERC3643Metadata | ERC3643MetadataFacet | Emits `UpdatedTokenInformation`. Only tokenOwner |
| `setSymbol(string)`     | ERC3643 Metadata | IERC3643Metadata | ERC20Internal           | ERC3643Metadata | ERC3643MetadataFacet | Emits `UpdatedTokenInformation`. Only tokenOwner |
| `setOnchainID(address)` | ERC3643 Metadata | IERC3643Metadata | ERC3643MetadataInternal | ERC3643Metadata | ERC3643MetadataFacet | Emits `UpdatedTokenInformation`. Only tokenOwner |
| `version()`             | ERC3643 Metadata | IERC3643Metadata | ERC3643MetadataInternal | ERC3643Metadata | ERC3643MetadataFacet | Returns current version string                   |
| `onchainID()`           | ERC3643 Metadata | IERC3643Metadata | ERC3643MetadataInternal | ERC3643Metadata | ERC3643MetadataFacet | Returns current onchainID address                |

- The IERC3643 interface methods related to **metadata** are fully implemented in `ERC3643Metadata`.
- The events and role modifiers affecting `setName`, `setSymbol`, and `setOnchainID` are applied in `ERC3643Metadata`.
- This module **does update ERC20 state variables (name, symbol)** in addition to maintaining its own storage for onchainID and version.

**Decision**

We chose **Option 2** because it allows access control and event emission to be handled directly in the external `ERC3643Metadata` contract, preventing the ERC20 module from inheriting unwanted regulatory specifications.

#### ERC3643 Regulatory Module

**Option 1**

| Method                         | Module             | Interface          | Internal                  | External          | Facet                  | Comment                                                                                |
| ------------------------------ | ------------------ | ------------------ | ------------------------- | ----------------- | ---------------------- | -------------------------------------------------------------------------------------- |
| `identityRegistry()`           | ERC3643 Regulatory | IERC3643Regulatory | ERC3643RegulatoryInternal | ERC3643Regulatory | ERC3643RegulatoryFacet | Returns current IdentityRegistry address                                               |
| `compliance()`                 | ERC3643 Regulatory | IERC3643Regulatory | ERC3643RegulatoryInternal | ERC3643Regulatory | ERC3643RegulatoryFacet | Returns current Compliance contract address                                            |
| `setIdentityRegistry(address)` | ERC3643 Regulatory | IERC3643Regulatory | ERC3643RegulatoryInternal | ERC3643Regulatory | ERC3643RegulatoryFacet | Emits `IdentityRegistryAdded`. Only tokenOwner                                         |
| `setCompliance(address)`       | ERC3643 Regulatory | IERC3643Regulatory | ERC3643RegulatoryInternal | ERC3643Regulatory | ERC3643RegulatoryFacet | Emits `ComplianceAdded`. Calls `bindToken` on the compliance contract. Only tokenOwner |

- The IERC3643 interface methods related to **regulatory infrastructure** are fully implemented in `ERC3643Regulatory`.
- Internal storage tracks the identity registry and compliance contract addresses.
- Events and access control are enforced in the external contract.
- This module **does not modify ERC20 state variables**; it only manages references to external regulatory contracts.
- This design isolates regulatory infrastructure from ERC20 base logic.

Other methods consume `identityRegistry()` and `compliance()` but are not part of this interface. (i.e **Mint** requires `_to` to be verified in `identityRegistry()` and validated by `compliance()`. )

**Decision**

We chose to implement regulatory infrastructure as a dedicated module to keep references to `IdentityRegistry` and `Compliance` isolated from the ERC20 base logic, while still allowing other modules (e.g. **Mint**, **Burn**) to consume them for validation.

#### ERC3643 Freeze Module

**Option 1**

| Method                                   | Module         | Interface      | Internal              | External      | Facet              | Comment                                   |
| ---------------------------------------- | -------------- | -------------- | --------------------- | ------------- | ------------------ | ----------------------------------------- |
| `setAddressFrozen(address,bool)`         | ERC3643 Freeze | IERC3643Freeze | ERC3643FreezeInternal | ERC3643Freeze | ERC3643FreezeFacet | Emits `AddressFrozen`. Only tokenAgent    |
| `freezePartialTokens(address,uint256)`   | ERC3643 Freeze | IERC3643Freeze | ERC3643FreezeInternal | ERC3643Freeze | ERC3643FreezeFacet | Emits `TokensFrozen`. Only tokenAgent     |
| `unfreezePartialTokens(address,uint256)` | ERC3643 Freeze | IERC3643Freeze | ERC3643FreezeInternal | ERC3643Freeze | ERC3643FreezeFacet | Emits `TokensUnfrozen`. Only tokenAgent   |
| `isFrozen(address)`                      | ERC3643 Freeze | IERC3643Freeze | ERC3643FreezeInternal | ERC3643Freeze | ERC3643FreezeFacet | Returns freezing status of an address     |
| `getFrozenTokens(address)`               | ERC3643 Freeze | IERC3643Freeze | ERC3643FreezeInternal | ERC3643Freeze | ERC3643FreezeFacet | Returns amount of partially frozen tokens |

- The IERC3643 interface methods related to **freezing** are fully implemented in `ERC3643Freeze`.
- Events and access control (`onlyTokenAgent`) are applied in the external contract.
- Internal storage tracks frozen status and partially frozen token amounts.
- This design isolates freeze logic, while still being consumed by other modules like Mint/Burn/Transfer.
- This module does **not modify ERC20 state variables**; it maintains separate freeze state variables.
- This design isolates freeze logic, while still being consumed by other modules like Mint/Burn/Transfer.

**Decision**

We chose to implement the freeze functionality as a **dedicated module** (`ERC3643Freeze`) because:

- The ERC-3643 standard specifies explicit freezing and partial freezing methods that must be enforced by **token agents**.
- Freezing logic directly impacts the execution of Mint, Burn, and Transfer operations, but does not belong to ERC20 base logic.
- Keeping freeze logic isolated improves maintainability and testing while enabling clearer enforcement of access control and event emission.

#### ERC3643 Control Module

**Option 1**

| Method                                    | Module          | Interface       | Internal              | External       | Facet               | Comment                                                                                         |
| ----------------------------------------- | --------------- | --------------- | --------------------- | -------------- | ------------------- | ----------------------------------------------------------------------------------------------- |
| `forcedTransfer(address,address,uint256)` | ERC3643 Control | IERC3643Control | -                     | ERC3643Control | ERC3643ControlFacet | Requires agent role, IR verification of recipient, auto-unfreeze logic, calls `_transfer`       |
| `mint(address,uint256)`                   | ERC3643 Control | IERC3643Control | -                     | ERC3643Control | ERC3643ControlFacet | Requires agent role, IR verification of recipient, calls `_mint` (respects hooks/cap/snapshots) |
| `burn(address,uint256)`                   | ERC3643 Control | IERC3643Control | -                     | ERC3643Control | ERC3643ControlFacet | Requires agent role, auto-unfreeze logic if needed, calls `_burn`                               |

- The IERC3643 interface methods related to **control operations** (forced transfer, mint, burn) are fully implemented in `ERC3643Control`.
- All functions are restricted to `onlyRole(_TOKEN_AGENT_ROLE)` and `whenNotPaused`.
- **Identity Registry** is checked for recipient addresses in `forcedTransfer` and `mint`.
    - If not verified, reverts with custom error `RecipientNotVerified(address)`.
- **Freeze / Unfreeze integration**:
    - If insufficient free balance but total balance is sufficient, `_unfreezePartialTokens` is called before the primitive operation.
    - Emits `TokensUnfrozen(address,uint256)` when auto-unfreeze occurs.
- **Primitives**:
    - All methods delegate to `_transfer`, `_mint`, `_burn` in `ERC20Internal` through `ERC20InternalCommon`.
    - Ensures hooks like `_beforeTokenTransfer` and `_afterTokenTransfer` (snapshots, cap checks, etc.) are never bypassed.

**Custom errors**

- New: `RecipientNotVerified(address recipient)` defined in `IERC3643Control`.
- Reuse: `TransferAmountExceedsBalance()` and `BurnAmountExceedsBalance()` from `IERC20Isbe`.

**Compliance hooks (debt)**

- Calls to `ICompliance.transferred`, `created`, and `destroyed` are not yet included.
- Left as **technical debt** to be integrated together with full Compliance validation.

**Cap integration**

- `ERC20CappedFacet` is not installed in 3643 deployments to avoid exposing mint via that path.
- If a supply cap is desired:
    - `ERC3643Control` must initialize `ERC20CappedInternal` storage and expose cap management methods.
    - The `mint` function of Control must include `_checkCap(_amount)` before calling `_mint`.

**Burn semantics**

- Unlike ERC20Burnable, burns in ERC-3643 are **agent-only**.
- `burn(address,uint256)` here is equivalent to a **forced burn**: the agent can destroy tokens from any account, with auto-unfreeze if needed.
- `burnFrom` is not implemented, as allowance-based burns are not compatible with ERC-3643 governance.

**Decision**

We chose to implement control operations in a dedicated module (`ERC3643Control`) because:

- ERC-3643 requires **agent-only authority** for mint, burn, and forced transfer.
- Identity verification and freeze integration are specific to 3643 and not present in ERC20 extensions.
- Reimplementing these functions avoids mixing regulatory logic into ERC20 base modules.
- Extensibility is preserved for cap checks and Compliance hooks.

### 5. Internal common aggregation

- All ERC-3643 modules that introduce **their own storage and internal logic**  
  (`Metadata`, `Regulatory`, `Freeze`, and `Control`)  
  are aggregated in **`ERC3643InternalCommon`**.

- External contracts (`ERC3643Metadata`, `ERC3643Regulatory`, `ERC3643Freeze`, `ERC3643Control`)  
  extend `ERC3643InternalCommon` to ensure **cross-module interoperability**.

- Modules already defined in **Core** (`Pause`, `Ownable`, `Access`)  
  continue to be inherited directly via `Common` and do not require ERC3643-specific internals.

## Benefits

- Aligns with Diamond architecture principles by isolating regulatory logic.
- Improves maintainability and testability through modular separation.
- Prevents undesired inheritance of ERC3643-specific behavior in base ERC20 modules.
- Enables clearer access control and event emission boundaries.

## Implementation phases

- ERC3643Metadata module: Define storage and encapsulation in ERC3643MetadataInternal, implement public methods with access control and event logic in ERC3643Metadata, and expose introspection via ERC3643MetadataFacet.

Note: Other modules will be added progressively following this structure.
