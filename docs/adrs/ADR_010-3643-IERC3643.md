## Context

The ERC-3643 standard defines a set of interfaces to support regulatory-compliant token operations. These interfaces are published under the ERC-3643 GitHub repository [https://github.com/ERC-3643/ERCs/blob/master/assets/erc-3643/interfaces] and include components for identity, compliance, recovery, freezing, and more.

Among them, IERC3643 is the main interface that directly extends IERC20, and serves as the entry point for most of the standard's regulatory and operational features.

However, IERC3643 is defined as a monolithic interface, which is incompatible with our modular design principles based on the Diamond pattern (EIP-2535).

## Unified identity and compliance validation model

This architecture does not rely on onchainID, ERC3643 IdentityRegistry, or external compliance contracts. Instead:

- Only wallets with a valid identity in the DID (Decentralized Identifier) system can interact with the network and the token contract.
- Identity validation is enforced at the access control layer, not through onchain registry checks.
- Compliance logic is fully integrated within the Diamond architecture and enforced internally by the InternalCommon contracts.
- All compliance checks are performed inside the unified logic, without calling a separate compliance contract.

As a consequence, any method or module from the original ERC-3643 standard that depends on onchain identity registry logic, direct management of onchainID, or external compliance contracts is omitted or adapted to this internal model.

This approach provides greater flexibility, aligns with decentralized identity standards, and maintains regulatory compliance through granular roles and modular logic.

## Decision

### 1. Segregation of IERC3643 into functional modules

To align with our Diamond architecture, the monolithic IERC3643 interface will be split into independent functional modules, each implemented through:

- A dedicated interface (e.g., IERC3643Freeze, IERC3643Recovery, etc.)
- An internal contract that encapsulates the business logic and manages storage
- An external contract that exposes public methods and delegates to the internal logic
- A facet that connects the external contract to the Diamond via delegatecall

When functionality is shared across multiple modules—such as token metadata, pause state, or access control—logic is centralized in abstract internal contracts (e.g., ERC203643InternalCommon, PauseInternalCommon)

### 2. Reuse of existing modules

To ensure compliance with ERC-3643 while maximizing modularity and reuse, the following strategy has been adopted:

- **Unified Architecture**: Create unified modules that work for both ERC20 and ERC3643 standards
- **Automatic Behavior Adaptation**: Internal logic adapts based on ERC3643 initialization.
- **Role Unification**: Merge similar roles while maintaining granular permissions

### 3. Conditional internal behavior

The internal logic of the modules dynamically adapts based on whether the environment has been initialized as ERC-3643 compatible. This configuration affects both access control and operation execution, enabling additional validations and specific restrictions to be applied only when the context requires it.

#### ERC203643 Controller Module

| Method                                              | Module               | Interface            | Internal      | External            | Facet                    | Returns | Events                                                           | Comment                                                                    |
| --------------------------------------------------- | -------------------- | -------------------- | ------------- | ------------------- | ------------------------ | ------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `forceTransfer(address,address,uint256)`            | ERC203643 Controller | IERC203643Controller | ERC20Internal | ERC203643Controller | ERC203643ControllerFacet | `bool`  | `ForceTransfer` + `Transfer` + `TokensUnfrozen`\*                | **Unified**: ERC20 simple transfer / ERC3643 with identity + auto-unfreeze |
| `forceBurn(address,uint256)`                        | ERC203643 Controller | IERC203643Controller | ERC20Internal | ERC203643Controller | ERC203643ControllerFacet | `void`  | `ForceBurn` + `Transfer` + `TokensUnfrozen`\*                    | **Unified**: ERC20 simple burn / ERC3643 with auto-unfreeze                |
| `batchForceTransfer(address[],address[],uint256[])` | ERC203643 Controller | IERC203643Controller | ERC20Internal | ERC203643Controller | ERC203643ControllerFacet | `void`  | `ForceTransfer` + `Transfer` + `TokensUnfrozen`\* (per transfer) | **Batch**: Multiple force transfers in single transaction                  |
| `batchForceBurn(address[],uint256[])`               | ERC203643 Controller | IERC203643Controller | ERC20Internal | ERC203643Controller | ERC203643ControllerFacet | `void`  | `ForceBurn` + `Transfer` + `TokensUnfrozen`\* (per burn)         | **Batch**: Multiple force burns in single transaction                      |

**Implementation Details:**

- **Unified Logic**: Single implementation adapts behavior based on `_identityRegistry() != address(0)`
- **ERC20 Mode** (no IdentityRegistry):
    - Simple force operations via `ERC20Internal._transfer/_burn`
    - Events: `ForceTransfer`/`ForceBurn` + standard `Transfer` events only
- **ERC3643 Mode** (IdentityRegistry configured):
    - Identity verification in `ERC203643InternalCommon._beforeTokenTransfer`
    - Auto-unfreeze functionality for insufficient free balance
    - Events: `ForceTransfer`/`ForceBurn` + `Transfer` + conditional `TokensUnfrozen`
- **Batch Operations**:
    - Allow processing multiple force operations in a single transaction
    - Each operation in the batch emits individual events
    - **Gas Warning**: Large batches may exceed gas limits - use with caution
    - Array length validation ensures consistent parameter arrays
- **Access Control**: All operations require `CONTROLLER_ROLE`
- **Pausable**: All operations respect `whenNotPaused` modifier

\*`TokensUnfrozen` event only emitted in ERC3643 mode when auto-unfreezing occurs

    - Events: Standard `Transfer` event (from address(0))

- **Pausable**: Mint operations respect `whenNotPaused` modifier
- **Previous Interface**: Replaces `IERC20Capped` with unified functionality

### 6. ERC20 primitive impacts in ERC3643 mode

#### Updated Primitive Operation Behavior

This section describes how mint, burn, and transfer operations behave in each mode, based on the actual contract logic:

**ERC20 Mode:**

- Standard ERC20 logic applies for all primitives (mint, burn, transfer).
- No compliance or freeze checks beyond basic balance validation.
- All facets are available, including user-initiated burns.

**ERC3643 Mode (Compliance Activated):**

- When compliance is activated, the contract operates in ERC3643 mode and compliance checks are enforced for all primitives (mint, burn, transfer).
- Compliance checks can be bypassed by accounts with the compliance role.
- Freeze logic is always enforced: sender and recipient must not be frozen, and sufficient free balance is required for transfers.
- Controller and recovery roles can trigger auto-unfreeze for force operations (transfer/burn).
- User-initiated burns are not exposed; only force burns via controller are allowed.

**Other Notes:**

- `approve`, `allowance`, `balanceOf`, and `totalSupply` remain standard in all modes.
- Facet exposure: In ERC20 mode, all facets are available. In ERC3643 mode, user burn facet is not exposed; only controllers can burn.
- Enhanced behaviors are automatically applied in `ERC203643InternalCommon._beforeTokenTransfer` depending on the presence of an identity registry.

### 7. Unified role architecture

**Context:**
The ERC3643 originally defines two main roles based on the interface comments:

- `TOKEN_OWNER_ROLE`: For "owner of the token smart contract" operations (metadata and regulatory setup)
- `TOKEN_AGENT_ROLE`: For "wallet set as agent of the token" operations (operational functions)

While ERC20 used specific roles like `CONTROLLER_ROLE` and `MINTER_ROLE`.

**Decision:**
Implement maximum granular role architecture maintaining ERC3643 semantics:

**Owner-level roles (infrastructure setup - granular breakdown of TOKEN_OWNER_ROLE):**

**METADATA_ROLE**: For token metadata management - `setName`, `setSymbol` (token branding)

**Agent-level roles (operational functions - granular breakdown of TOKEN_AGENT_ROLE):**

- **CONTROLLER_ROLE**: For force operations
    - `forceTransfer`, `forceBurn` (replaces ERC20 controller functionality)
- **MINTER_ROLE**: For minting operations
    - `mint` (maintains existing ERC20Capped role)
- **FREEZE_ROLE**: For freeze/unfreeze operations
    - `setAddressFrozen`, `freezePartialTokens`, `unfreezePartialTokens`
- **PAUSE_ROLE**: For pause/unpause operations
    - `pause`, `unpause`
- **CAP_ROLE**: For cap management
    - `setCap`, `initializeCap`
- **RECOVERY_ROLE**: For recovery operations
    - `recoveryAddress` _(pending implementation)_
- **COMPLIANCE_ROLE**: For compliance bypass
    - Can bypass compliance checks for all primitives (mint, burn, transfer) when compliance is activated

**For wallets needing full ERC3643 "owner" functionality:**

- Assign owner roles: `METADATA_ROLE`
- This provides complete equivalence with original `TOKEN_OWNER_ROLE` but with granular control

**For wallets needing full ERC3643 "agent" functionality:**

- This provides complete equivalence with original `TOKEN_AGENT_ROLE` but with granular control

Assign operational roles: `CONTROLLER_ROLE` + `MINTER_ROLE` + `FREEZE_ROLE` + `PAUSE_ROLE` + `RECOVERY_ROLE` + `COMPLIANCE_ROLE`

\*`COMPLIANCE_ROLE` allows bypassing compliance checks for all primitives when compliance is activated

## Benefits

- **Unified Architecture**: Single codebase handles both ERC20 and ERC3643 standards
- **Automatic Adaptation**: Behavior changes based on regulatory context without code duplication
- **Maximum Role Granularity**: Each operation type has its own specific role
- **Organizational Flexibility**: Different teams can have different permission levels (metadata vs regulatory vs operational)
- **Diamond Compatibility**: Aligns with modular architecture principles
- **Reduced Complexity**: Eliminates need for separate ERC20 and ERC3643 implementations
- **Improved Maintainability**: Single point of logic for common operations
- **Regulatory Compliance**: Automatic enforcement of ERC3643 rules when IdentityRegistry is configured
- **Backwards Compatibility**: ERC20 behavior preserved when regulatory components are not initialized
